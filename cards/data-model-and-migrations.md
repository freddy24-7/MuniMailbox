# Data model, SQLAlchemy and Alembic

**Status:** Stage 1 notes added, questions open · **Stages:** 1, 3 · **Code:** `app/db/`, Alembic migrations

## In one sentence
The relational tables are described once as Python classes, accessed through repositories,
and changed over time through versioned migration scripts.

## Why it matters in this app
The data model *is* the privacy design: which table holds clear text, which holds
placeholders and which holds encrypted values decides what can leak. It also carries the
workflow (email status), the human decision (`Review`) and the evidence (`AuditEvent`).

## Core ideas
- **ORM model** — a Python class mapped to a table (SQLAlchemy 2.x, typed `Mapped[...]` columns).
- **Async session** — a unit of work; changes are committed together or not at all.
- **Repository** — a small class that hides queries, so agents and endpoints never write SQL.
- **Migration** — a script that moves the schema from one version to the next (Alembic);
  applied migrations are never edited, a new one is added.
- **Schema vs model** — Pydantic schemas are what crosses the API; ORM models are what is stored.
- **State machine** — the email status has a fixed set of values and allowed transitions (FR-4).

## In this project
Entities from the PRD: `Citizen`, `Case`, `Email`, `PiiMapping`, `Draft`, `Review`, `User`,
`AuditEvent` (plus `DocumentChunk` in ChromaDB).
- `Email.body_redacted` holds placeholders; the original body is stored encrypted.
- `Draft.text_redacted` holds placeholders only (acceptance criterion).
- `AuditEvent` is append-only — no update or delete path exists in its repository.
- One email can have several drafts; one draft can have several reviews.

## Notes from the build
### Stage 1 — 2026-10-10

**What was built**
- [app/db/models.py](../app/db/models.py): all eight PRD tables. The docstring at the top
  lists which columns hold personal data and in what form.
- [app/db/base.py](../app/db/base.py): a naming convention, so every constraint and index
  gets a predictable name (`fk_cases_citizen_id_citizens`) that later migrations can refer to.
- [app/db/migrations/](../app/db/migrations/): Alembic, with one migration, "initial schema".
  It was autogenerated from the models and then read through by hand.

**Decisions and why**
- Three deliberate differences from the PRD's table:
  - `Email.original_encrypted` holds sender, subject and body as one encrypted value.
  - `Email.subject_redacted` exists, because a subject line can contain personal data too.
  - `Review.edited_text_redacted` instead of `edited_text`, so the rule is in the name.
- Enums are stored as plain strings (`native_enum=False`). Adding a seventh topic is then a
  code change only; a native PostgreSQL enum type would need a migration.
- `topic`, `urgency`, `subject_redacted` and `body_redacted` on `Email` are nullable: they
  are filled in by agents, and "null" means "that agent has not run yet".
- All primary keys are UUIDs except `AuditEvent.id`, which is a sequence, because the hash
  chain needs one total order.
- Timestamps are `DateTime(timezone=True)`.

**Seen in practice**
- CI runs `alembic upgrade head` and then `alembic check`. The second command fails if the
  models and the migrations have drifted apart — the usual way to forget a migration.
- SQLite does not enforce foreign keys unless told to. The local test run (SQLite) would
  not catch a case pointing at a missing citizen; the CI run (PostgreSQL) would.

**Try it**
- `uv run alembic upgrade head --sql | less` — the SQL the migration produces, without running it.
- `docker compose exec postgres psql -U munimailbox -c '\d emails'`
- Add a column to a model, run `uv run alembic check`, read the message, undo the change.

**Not met yet**
- No repositories and no `relationship()` yet — nothing queries across tables so far.
- Status transitions are not enforced anywhere yet; `Email.status` accepts any of the six values (Stage 2).
- Nothing makes `AuditEvent` append-only yet beyond the comment (Stage 2).
